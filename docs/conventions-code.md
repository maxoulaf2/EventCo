# Conventions de code — SaaS de planification d'événements

Ce document complète le document de cadrage (`cadrage-projet-eventco.md`) et sert de référence de style/architecture à fournir à Claude Code. Objectif : garantir une cohérence sur toute la durée du projet, même après un reset de contexte.

---

## 1. Architecture backend — Clean Architecture + DDD

### 1.1 Structure des projets (solution .NET)

```
EventCo.sln
├── src/
│   ├── EventCo.Domain/           # Entités, Value Objects, interfaces de domaine, règles métier pures
│   ├── EventCo.Application/      # Use cases (Commands/Queries), interfaces des services externes, DTOs
│   ├── EventCo.Infrastructure/   # Implémentation EF Core, envoi d'email, SignalR, accès externes
│   └── EventCo.Api/              # Controllers, configuration, middlewares, DI, Program.cs
└── tests/
    ├── EventCo.Domain.Tests/
    ├── EventCo.Application.Tests/
    └── EventCo.Api.Tests/        # Tests d'intégration (WebApplicationFactory)
```

**Règle de dépendance** : `Domain` ne dépend de rien. `Application` dépend de `Domain`. `Infrastructure` et `Api` dépendent de `Application` (et implémentent ses interfaces). Aucune dépendance ne doit remonter dans le sens inverse.

### 1.2 Concepts DDD appliqués

- **Entités riches** : les entités du `Domain` (ex: `Event`, `EventTask`) encapsulent leurs règles métier via des méthodes (ex: `event.AssignTask(actingUserId, taskId, userId)`) plutôt que d'exposer des setters publics sur toutes les propriétés. On évite le modèle "anemic domain model".
- **Value Objects** quand c'est pertinent (ex: `Email` comme Value Object avec validation de format, plutôt qu'un simple `string`).
- **Agrégats** : `Event` est l'agrégat racine pour `EventParticipant` et `EventTask`. Toute modification de ces sous-entités passe par l'agrégat `Event`, qui garantit la cohérence (ex: on ne peut pas assigner une tâche à un utilisateur qui n'est pas participant).
- **Repositories** : interfaces définies dans `Domain` ou `Application` (ex: `IEventRepository`), implémentées dans `Infrastructure` avec EF Core. Un repository par agrégat racine (pas un repository générique par table).
  > **Décision (2026-09-07)** : à la demande du développeur, `Infrastructure` ne mappe plus les objets `Domain` directement comme entités EF Core (couplage jugé trop fort entre le modèle métier et le schéma de base). `Infrastructure/Persistence/Entities/` déclare ses propres classes de persistance, suffixées `Entity` (`UserEntity`, `MagicLinkTokenEntity`, `EventEntity`, `EventParticipantEntity`, `EventTaskEntity`) : classes anémiques, propriétés publiques en lecture/écriture, `Email` en `string` brute (pas de Value Object référencé) — seuls les enums `Domain` (`EventStatus`, `ParticipantRole`, `TaskCategory`) restent partagés, `Infrastructure` dépendant déjà de `Domain`. Les `IEntityTypeConfiguration<T>` et le `DbContext` (`DbSet<XxxEntity>`) portent désormais sur ces classes, pas sur les agrégats. Le schéma de base (tables/colonnes/index/FK) reste strictement identique — vérifié via `dotnet ef migrations add` (diff `Up`/`Down` vide), aucune migration nécessaire pour ce refactoring.
  >
  > Le mapping Entity ↔ Domain est fait par le repository, via des classes statiques dédiées (`Infrastructure/Persistence/Mapping/UserMapper.cs`, `MagicLinkTokenMapper.cs`, `EventMapper.cs`) : `ToDomain`/`ToEntity`, plus `ApplyToEntity` pour les mises à jour. Reconstituer un agrégat `Domain` à partir de son état persisté (Id existant, pas de re-validation métier) passe par une factory `internal static Reconstitute(...)` sur chaque classe `Domain` concernée (`User`, `MagicLinkToken`, `Event`, `EventParticipant`, `EventTask`), visible depuis `Infrastructure` via `<InternalsVisibleTo Include="EventCo.Infrastructure" />` (`EventCo.Domain.csproj`) — cohérent avec les constructeurs déjà `internal` de `EventParticipant`/`EventTask` (accès contrôlé, pas de setter public). Les anciens constructeurs privés sans paramètre (`private User()`, etc., et le constructeur protégé sans paramètre d'`Entity`), qui n'existaient que pour permettre à EF Core de matérialiser directement les objets `Domain`, ont été supprimés : devenus inutiles, EF Core ne touche plus jamais aux classes `Domain`.
  >
  > **Conséquence sur `IEventRepository.UpdateAsync`** : `Event` étant un agrégat avec collections enfants (`Participants`, `Tasks`), la mise à jour ne peut plus s'appuyer sur le change tracking EF Core implicite (l'objet `Domain` retourné par `GetByIdAsync` n'est plus l'entité trackée). `EventRepository.UpdateAsync` recharge l'`EventEntity` tracké (avec ses collections) et lui applique l'état courant de l'agrégat `Domain` via `EventMapper.ApplyToEntity`, qui synchronise les collections enfants (ajout/suppression/mise à jour par comparaison d'`Id`) plutôt que de tout recréer.
  >
  > **Piège EF Core (2026-09-07, tâche `InviteParticipant`)** : ajouter une **nouvelle** entité enfant (`EventParticipantEntity`/`EventTaskEntity`) à la collection d'un `EventEntity` déjà suivi par le `ChangeTracker` (typiquement `GetByIdAsync` puis `UpdateAsync` dans le même `DbContext`, via `Event.InviteParticipant`) fait échouer `SaveChangesAsync` avec `DbUpdateConcurrencyException` ("entity does not exist in the store"). Cause : ces entités ont un Id généré côté Domain (`Guid.NewGuid()`), mais restaient configurées `ValueGeneratedOnAdd` (comportement par défaut EF Core pour une clé `Guid`) — `DetectChanges` ne peut alors pas distinguer "nouvelle entité au Id déjà défini" d'"entité existante rechargée puis modifiée" quand elle apparaît dans une collection déjà suivie, et la marque à tort `Modified`. Non rencontré tant qu'un Command ajoute tout l'agrégat d'un bloc (`CreateEvent`, via `AddAsync`, où l'`Add` explicite cascade `Added` sans ambiguïté) ou ne modifie que des propriétés scalaires (`UpdateEvent`) — seul l'ajout d'un enfant à un agrégat *déjà chargé* déclenche le problème, donc à surveiller pour toute méthode du même genre (ex: lot 3, `AddTask` sur un `Event` chargé). **Solution** : `builder.Property(p => p.Id).ValueGeneratedNever()` dans `EventParticipantConfiguration`/`EventTaskConfiguration` — lève l'ambiguïté à la source (l'app est seule responsable de la génération de la clé), sans impact sur le schéma de base (vérifié via `dotnet ef migrations add`, diff `Up`/`Down` vide).
  >
  > **Piège du 2026-09-01 (§1.4, comparaison LINQ sur `u.Email.Value`) rendu obsolète par ce refactoring** : `UserEntity.Email`/`MagicLinkTokenEntity.Email` étant désormais de simples `string`, `UserRepository`/`MagicLinkTokenRepository` comparent directement `u.Email == email.Value` sans passer par le Value Object — le problème de traduction LINQ ne se pose plus pour ces repositories.
- **Use Cases explicites (CQRS léger)** : dans `Application`, chaque action métier est une classe dédiée (ex: `CreateEventCommand` / `CreateEventCommandHandler`, `GetEventByIdQuery` / `Handler`). MediatR est recommandé pour orchestrer ça proprement.
  > **Note (2026-08-31)** : MediatR est désormais sous licence payante en production (Lucky Penny Software, depuis 2025). En attendant une décision définitive du développeur, l'orchestration est assurée par une abstraction maison (`EventCo.Application/Common/Messaging/` : `ICommand`, `ICommandHandler<T>`, `ICommandDispatcher`) qui reproduit le strict nécessaire de l'API MediatR sans dépendance externe. **Tous les Commands des lots suivants doivent suivre ce pattern** jusqu'à révision de cette note.
  >
  > **Extension (2026-09-01)** : ajout d'un pendant à réponse — `ICommand<TResponse>` / `ICommandHandler<TCommand,TResponse>` / `ICommandDispatcher.Send<TResponse>(ICommand<TResponse>, ...)` — pour les use cases qui doivent renvoyer un résultat (ex: `VerifyMagicLinkCommand` renvoie les infos de session). À utiliser aussi pour les futures Queries du lot 2 (`GetEventByIdQuery`, etc.), plutôt que d'introduire une interface `IQuery` séparée. `ICommand` et `ICommand<TResponse>` sont volontairement sans lien d'héritage entre elles pour éviter une ambiguïté de surcharge sur `Send`.
- **Domain Events** (optionnel, à introduire si utile) : ex: `TaskAssignedDomainEvent` déclenché par l'agrégat, consommé ensuite pour notifier via SignalR ou envoyer un email, sans coupler le domaine à l'infrastructure.
  > **Décision (2026-09-08)** : introduits pour les 5 handlers de tâches, à la demande du développeur, revenant sur la décision du 2026-09-08 (tâche "Diffusion temps réel des tâches", ci-dessus dans le journal) qui les avait écartés faute de second abonné. `Entity` (`EventCo.Domain/Common/`) porte désormais `DomainEvents`/`AddDomainEvent`/`ClearDomainEvents` ; l'agrégat `Event` lève un event (`EventCo.Domain/Events/DomainEvents/`) dans chacune de ses méthodes métier concernées (`AddTask`, `AssignTask`, `CompleteTask`/`ReopenTask`, `RemoveTask`). Propagation via un mediator maison symétrique à `ICommand`/`ICommandHandler`/`ICommandDispatcher` (même raison : MediatR écarté pour licence, cf. décision du 2026-08-31) : `IDomainEventHandler<T>`/`IDomainEventDispatcher`/`DomainEventDispatcher` (`EventCo.Application/Common/Messaging/`), plusieurs handlers possibles par event (`GetServices`, pas `GetRequiredService`, contrairement aux Commands). Les handlers `CreateTask`/`AssignTask`/`CompleteTask`/`ReopenTask`/`DeleteTask` perdent leur dépendance à `ITaskRealtimeNotifier` (déplacée dans des `*DomainEventHandler` dédiés, `EventCo.Application/Events/DomainEvents/`) mais **gardent `IEventRepository`** (lecture `GetByIdAsync` + écriture explicite `UpdateAsync`/`AddAsync`) : une persistance entièrement pilotée par les domain events (sans appel repository explicite dans le handler) aurait réintroduit un tracking implicite des agrégats Domain, à l'opposé de la décision du 2026-09-07 (mapping Domain ↔ EF explicite via `EventMapper`, pas d'entités EF mappées directement sur le Domain) — écarté pour un gain jugé surtout esthétique sur un projet de cette taille.
  >
  > **Travail préparatoire associé : Unit of Work.** `EventRepository`/`UserRepository`/`MagicLinkTokenRepository` appelaient chacun `SaveChangesAsync` en interne à chaque écriture ; ils ne font plus que du staging EF. Nouveau port `IUnitOfWork` (`EventCo.Application/Common/Interfaces/`), implémenté par `UnitOfWork` (`EventCo.Infrastructure/Persistence/`, délègue à `EventCoDbContext.SaveChangesAsync`). `CommandDispatcher` appelle désormais `unitOfWork.SaveChangesAsync` une seule fois après l'exécution du handler, puis dispatche les domain events accumulés (collectés via `DomainEventCollector`, rempli par les repositories à chaque `AddAsync`/`UpdateAsync`) — dans cet ordre, pour que les notifications SignalR n'aient lieu qu'après un commit réussi. `EventCoDbContext` était déjà `Scoped` par défaut (`AddDbContext`), donc déjà borné à la requête HTTP ; le changement est de centraliser l'appel à `SaveChangesAsync` plutôt que de changer sa portée.
  >
  > **Piège rencontré** : deux steps Gherkin de `Application.Tests` (`InviteParticipantSteps`/`GetEventByIdSteps`) écrivaient directement via `IUserRepository.AddAsync` en dehors de tout `ICommandDispatcher.Send` (fixture de test, pas de Command dédiée pour "un compte existe déjà"). Sans le `SaveChangesAsync` implicite qu'avait `AddAsync` jusqu'ici, ces écritures restaient non committées jusqu'au prochain dispatch de commande — un scénario `InviteParticipant` créait alors un second compte pour le même email, le premier restant invisible aux requêtes EF tant qu'il n'était pas commité. Corrigé en committant explicitement via `IUnitOfWork.SaveChangesAsync` dans ces deux steps. À surveiller pour tout futur step de test qui écrirait directement via un repository hors `ICommandDispatcher`.
  >
  > **Évolution (2026-09-10)** : à la demande du développeur, `IEventRepository`/`IUserRepository`/`IMagicLinkTokenRepository` n'exposent plus chacun qu'une seule méthode d'écriture, `ApplyAsync(agrégat, ct)` (remplace `AddAsync`/`UpdateAsync`), qui inspecte les domain events portés par l'agrégat (`switch` sur le type, une méthode privée dédiée par cas — pas de réflexion ici, contrairement à `DomainEventDispatcher`) pour ne toucher que les lignes réellement concernées, plutôt que de passer par un diff générique de tout l'agrégat. `EventMapper.ApplyToEntity`/`SyncChildren` (diff générique Participants/Tasks) sont supprimés : chaque insertion/suppression d'enfant (`EventParticipantEntity`/`EventTaskEntity`) est désormais une opération ciblée déclenchée par son event (`ParticipantInvitedDomainEvent`, `TaskCreatedDomainEvent`...), et chaque mise à jour scalaire (`EventDetailsUpdatedDomainEvent`, `ParticipantRoleChangedDomainEvent`, `TaskStatusChangedDomainEvent`...) résout l'entité ciblée via `DbContext.FindAsync` (résolution depuis le ChangeTracker local sans requête SQL si déjà suivie via un `GetByIdAsync` antérieur dans la même requête) plutôt que de recharger tout l'agrégat. `DeleteAsync` (`IEventRepository`, suppression de tout l'agrégat) reste **en dehors de ce pattern** : ce n'est pas une mutation exprimée par un domain event, le Command sait déjà explicitement qu'il veut supprimer.
  >
  > **Domain events ajoutés pour toutes les mutations, pas seulement celles déjà exercées par un Command** (`EventCreatedDomainEvent`, `EventDetailsUpdatedDomainEvent`, `EventStatusChangedDomainEvent` (`Cancel`/`Complete`), `ParticipantInvitedDomainEvent`, `ParticipantJoinedDomainEvent` (`ConfirmParticipant`), `ParticipantRoleChangedDomainEvent` (`PromoteToOrganizer`/`DemoteToParticipant`), `ParticipantRemovedDomainEvent`, `TaskUnassignedDomainEvent`, plus `UserCreatedDomainEvent`/`UserProfileUpdatedDomainEvent` et `MagicLinkTokenCreatedDomainEvent`/`MagicLinkTokenConsumedDomainEvent`) : `ApplyAsync` étant devenu le seul chemin d'écriture, une mutation du domaine sans event correspondant ne serait silencieusement jamais persistée — `Cancel`/`Complete`/`ConfirmParticipant`/`RemoveParticipant`/`UnassignTask`/`User.UpdateProfile` ne sont exercées par aucun Command aujourd'hui (vérifié par recherche exhaustive) mais sont couvertes par cohérence/précaution. `ApplyAsync` lève une `InvalidOperationException` explicite pour tout type de domain event non géré, plutôt que de l'ignorer silencieusement.
  >
  > **Forme des payloads** : les events déjà en place pour les tâches (`TaskCreatedDomainEvent`, `TaskAssignedDomainEvent`, `TaskStatusChangedDomainEvent`) transportent l'entité `EventTask` complète — conservés tels quels, car ils ont un second consommateur (`ITaskRealtimeNotifier` via les `*DomainEventHandler` de notification) qui en a besoin sans dépendre de l'agrégat en mémoire. Les nouveaux events (Event/Participant/User/MagicLinkToken), qui n'ont aujourd'hui aucun consommateur de notification, ne transportent que les **identifiants** nécessaires (ex: `ParticipantInvitedDomainEvent(EventId, ParticipantId)`) : la méthode privée du repository relit l'état courant directement sur l'agrégat passé à `ApplyAsync` (`@event.Participants.Single(p => p.Id == ...)`), toujours en mémoire à ce stade. Seuls les events de suppression (`ParticipantRemovedDomainEvent`, `TaskDeletedDomainEvent`) transportent les IDs bruts sans passer par l'agrégat, l'entité n'y étant plus consultable une fois retirée de la collection.

### 1.3 Conventions de nommage (backend)
- Classes/interfaces : `PascalCase`. Interfaces préfixées par `I` (`IEventRepository`).
- Commands/Queries : suffixe explicite (`CreateEventCommand`, `GetEventByIdQuery`).
- DTOs exposés par l'API : suffixe `Dto` ou `Response`/`Request` (`EventResponse`, `CreateEventRequest`).
- Fichiers : un type public par fichier, nom de fichier = nom du type.
- Enums : au singulier (`EventStatus`, pas `EventStatuses`).

### 1.4 Tests
- `Domain.Tests` : tests unitaires purs sur les règles métier des entités/agrégats (pas de mock nécessaire, pas de DB).
- `Application.Tests` : tests d'intégration des Commands/Queries écrits en **Gherkin** (fichiers `.feature`, en français, exécutés via **Reqnroll** — le fork open-source activement maintenu de SpecFlow, dont le développement communautaire s'est arrêté en 2024) plutôt que des tests unitaires avec mocks (Moq/NSubstitute).
  > **Décision (2026-08-31)** : à la demande du développeur, pas de mocking de repositories — chaque Command/Query est testé de bout en bout via le vrai `ICommandDispatcher`/`CommandDispatcher`, la vraie validation FluentValidation, et un vrai `EventCoDbContext` (EF Core provider **InMemory**, pour la rapidité — cf. `tests/EventCo.Application.Tests/Support/ApplicationTestHostBuilder.cs`). Seuls les ports vers des systèmes externes (ex: `IEmailSender`, `IDateTimeProvider`) sont remplacés par de simples doublons de test (`tests/EventCo.Application.Tests/TestDoubles/`), pas par une librairie de mock. Un sous-ensemble de scénarios nominaux sera complété plus tard avec un vrai PostgreSQL (Testcontainers), en plus (pas en remplacement) de la majorité des tests en InMemory.
  >
  > Structure par feature : `Auth/RequestMagicLink/RequestMagicLink.feature` + `RequestMagicLinkSteps.cs` (classe `[Binding]`) à côté du Command testé. Les méthodes de step suivent le texte du Gherkin (pas la convention `MethodName_Scenario_ExpectedResult` ci-dessous, propre aux tests xUnit classiques).
- `Api.Tests` : tests d'intégration bout-en-bout écrits en **Gherkin/Reqnroll** (mêmes conventions que `Application.Tests` ci-dessus), via `WebApplicationFactory<Program>` + un vrai PostgreSQL démarré à la volée avec **Testcontainers** (`postgres:16-alpine`, cohérent avec `docker-compose.yml`).
  > **Décision (2026-09-01)** : à la demande du développeur, tous les tests d'`Api.Tests` suivent aussi l'approche Gherkin (pas seulement `Application.Tests`) — un vrai appel HTTP (`HttpClient` du `WebApplicationFactory`) contre l'API complète, avec un vrai PostgreSQL (pas d'InMemory ici, contrairement à `Application.Tests` : le but de cette couche est justement de vérifier le comportement contre le vrai moteur relationnel). Le conteneur Postgres + le `WebApplicationFactory` sont démarrés **une seule fois pour tout le run** via des hooks Reqnroll `[BeforeTestRun]`/`[AfterTestRun]` (`tests/EventCo.Api.Tests/Support/Hooks.cs`, `ApiWebApplicationFactory.cs`) plutôt qu'un `IClassFixture` xUnit par scénario, pour éviter de payer le coût de démarrage du conteneur à chaque scénario. Chaque scénario doit donc utiliser des données distinctes (ex: emails uniques) pour rester indépendant des autres, faute d'un reset de base entre scénarios (pas encore mis en place).
  >
  > Piège rencontré : comparer une propriété interne du Value Object `Email` dans un prédicat LINQ traduit en SQL (`u.Email.Value == ...`) échoue avec le provider Npgsql (`InvalidOperationException`, traduction impossible) — `HasConversion` n'apprend à EF Core à convertir que la propriété mappée dans son ensemble (`User.Email`), pas ses membres internes, donc `.Value` n'est pas traduisible. Le provider InMemory masque le problème car il évalue le prédicat côté client. Solution : comparer le Value Object entier plutôt que sa propriété interne (`u.Email == email`) — EF Core pousse alors les deux côtés à travers le converter et génère bien un `WHERE` SQL, sans matérialiser toute la table.
  >
  > Structure par feature : `Auth/RequestLink/RequestLink.feature` + `RequestLinkSteps.cs`, même organisation que `Application.Tests`.
- Convention de nommage des tests xUnit classiques (`Domain.Tests` uniquement, désormais) : `MethodName_Scenario_ExpectedResult` (ex: `AssignTask_UserNotParticipant_ThrowsDomainException`).

## 2. Architecture frontend — React

### 2.1 Structure des dossiers

```
src/
├── features/              # Un dossier par fonctionnalité métier (feature-based, pas type-based)
│   ├── events/
│   │   ├── components/
│   │   ├── hooks/
│   │   ├── api.ts          # Appels API spécifiques à la feature
│   │   └── types.ts
│   ├── tasks/
│   └── auth/
├── shared/
│   ├── components/         # Composants UI génériques réutilisables (Button, Modal...)
│   ├── hooks/
│   └── lib/                # Config axios/fetch, helpers, config SignalR
├── App.tsx
└── main.tsx
```

On privilégie une organisation **par feature** plutôt que par type technique (pas de gros dossier `components/` fourre-tout) : ça facilite le travail de Claude Code sur un périmètre isolé sans naviguer dans tout le projet.

### 2.2 Conventions
- Composants : `PascalCase`, un composant par fichier (`TaskList.tsx`).
- Hooks custom : préfixe `use` (`useEventTasks.ts`).
- Typage strict : TypeScript en mode `strict`, pas de `any` sauf cas justifié en commentaire.
- State management : commencer avec les hooks React natifs (`useState`, `useContext`) + **React Query** pour la gestion des appels API (cache, invalidation, loading states) — évite d'introduire Redux/Zustand tant que le besoin ne s'en fait pas sentir.
- Styles : Tailwind CSS exclusivement, pas de CSS-in-JS ni de fichiers `.css` séparés sauf cas exceptionnel (ex: animations complexes).
- Mobile-first : toute classe Tailwind responsive s'écrit du plus petit écran vers le plus grand (`class="text-sm md:text-base"`, jamais l'inverse).
- **Sélection dans les tests via `data-testid`** (`kebab-case`, nom spécifique du composant/élément, ex: `task-list-category-filter`) plutôt que par rôle/label/texte affiché — cf. §2.3 ci-dessous pour le détail et la justification.

### 2.3 Tests frontend
> **Décision (2026-09-02)** : à la demande du développeur, trois couches de tests distinctes, toutes écrites en **Gherkin** (`.feature` en français, `# language: fr`, même style que le backend §1.4), avec un outil différent par couche selon ce qu'elle vérifie.

| Couche | Outil | Commande | Ce qu'elle vérifie |
|---|---|---|---|
| Comportement (back mocké) | **Vitest** + React Testing Library + **MSW**, Gherkin via `@amiceli/vitest-cucumber` | `npm test` / `npm run test:watch` | Le rendu et les interactions du client, indépendamment du back (appels réseau interceptés) |
| Non-régression visuelle | **Playwright** (`toHaveScreenshot`) + **playwright-bdd** | `npm run test:visual` (cf. note CI ci-dessous pour `:update`) | L'apparence des pages à plusieurs tailles d'écran (projets `mobile`/`tablet`/`desktop`) |
| E2E nominal | **Playwright** + **playwright-bdd**, contre une stack dédiée | `npm run test:e2e` (tout inclus, cf. ci-dessous) | Le parcours réel de bout en bout, sans mock |

> **Décision (2026-09-17)** : à la demande du développeur, tout composant/élément testable (formulaires, champs, boutons, liens, messages d'erreur/succès, badges, lignes de liste...) porte un attribut `data-testid` dédié, et les trois couches de tests ci-dessus sélectionnent **exclusivement** via cet attribut (`screen.getByTestId(...)` / `page.getByTestId(...)`) plutôt que par rôle ARIA, `label`/`name` accessible ou texte affiché — ces derniers avaient déjà nécessité des contournements (`getByLabel('Catégorie', { exact: true })` pour lever l'ambiguïté avec « Filtrer par catégorie », cf. `apparence-detail-evenement.steps.ts`) et restent fragiles au moindre changement de copie/wording. Convention de nommage : `kebab-case`, nom spécifique du composant/élément plutôt que générique (ex: `task-list-category-filter` pour le filtre de catégorie de `TaskList`, `create-event-submit-button` pour le bouton de soumission de `CreateEventPage`).
>
> **Élément répété dans une liste** (ligne de participant, de tâche, d'événement du tableau de bord) : le `data-testid` est suffixé par l'id métier de l'élément plutôt que d'être statique (ex: `participant-row-${participant.userId}`, `task-item-${task.id}`, `event-list-item-${event.id}`) — un test-id statique répété sur chaque ligne ne permettrait pas de cibler une ligne précise sans repasser par le texte affiché, à l'opposé de l'objectif recherché. **Point d'architecture non couvert jusqu'ici par ce document, tranché avec le développeur au moment de cette tâche (rule 7)** : cette convention suppose que l'id métier de l'élément est connu du test. C'est le cas pour les couches Comportement/Visuelle (données mockées, ids fixes comme `event-1`/`task-1`) mais pas toujours pour la couche E2E, où un événement créé via un appel direct à l'API réelle (`mes-evenements.steps.ts`) reçoit un id généré serveur — la réponse de création est alors lue pour retenir cet id (`WeakMap<Page, string>`, une entrée par `page` de test) plutôt que de retomber sur une recherche par texte pour cette seule couche.
>
> Suite complète frontend rejouée après ce changement : 106/106 verts (comportement) ; non-régression visuelle : `bddgen`/`playwright test --list` valident les 33 scénarios (aucune étape Gherkin orpheline) et un run local complet ne remonte que des écarts de pixels (~2 %, rendu de police Windows/Linux, cf. décision du 2026-09-03 ci-dessous) sur les captures déjà existantes — aucun sélecteur en échec, confirmant que le passage aux `data-testid` n'a pas cassé la résolution des éléments ; capture générée localement pour le seul scénario encore sans référence supprimée après vérification, jamais une baseline valide sous Windows (cf. décision ci-dessous). E2E non rejouée dans cet environnement (nécessite Docker), vérifiée uniquement par compilation (`tsc --noEmit`) et génération des specs (`bddgen`).

> **Definition of done (2026-09-08)** : ces trois couches ne sont pas optionnelles au cas par cas. Toute tâche frontend qui ajoute une page/un composant significatif, ou qui modifie sensiblement l'apparence d'une page existante, n'est considérée terminée que si un scénario de non-régression visuelle (`tests/visual/features/` + `steps/`, captures générées via l'image Docker Playwright — cf. note CI plus bas, jamais `npm run test:visual:update` en local) a été ajouté ou mis à jour, au même titre que la couche comportement. **Contre-exemple à ne pas reproduire** : la page de création d'événement (journal du 2026-09-08) livrée avec sa seule couche comportement, la couche visuelle ajoutée seulement après coup en tâche corrective séparée.

Structure : les trois couches vivent dans `tests/`, chacune avec ses propres `features/` et `steps/` (un sous-dossier par feature, ex: `auth/`, `events/`) plutôt que colocalisées avec le code de `src/features/` — `tests/behavior/` pour la couche comportement (ex: `tests/behavior/features/auth/RequestMagicLink.feature` + `tests/behavior/steps/auth/RequestMagicLink.steps.tsx`), `tests/e2e/` et `tests/visual/` (chacun avec en plus son `playwright.config.ts` propre) pour les deux couches Playwright, qui testent des parcours transverses plutôt qu'un composant isolé.
> **Décision (2026-09-04)** : à la demande du développeur, la couche comportement a été déplacée de `src/features/**` (colocalisée avec le composant testé) vers `tests/behavior/`, pour que le code de test soit séparé du code de prod comme les deux autres couches. `vitest.config.ts` inclut désormais `tests/behavior/**/*.steps.{ts,tsx}` (et n'exclut plus que `tests/e2e/**`/`tests/visual/**`, plus finement que l'ancien `tests/**`).

**E2E nominal — stack dédiée, isolée de la base de dev.** `npm run test:e2e` ne suppose plus `docker compose up -d postgres api` démarré à la main : `globalSetup`/`globalTeardown` (`tests/e2e/global-setup.ts`/`global-teardown.ts`) démarrent et arrêtent automatiquement `docker-compose.e2e.yml` (services `postgres-e2e`/`mailpit-e2e`/`api-e2e`, projet Compose `eventco-e2e`, ports `5433`/`8025`/`5001`, volume jetable) autour de la suite.
> **Décision (2026-09-02)** : à la demande du développeur, cette stack ne doit jamais interférer avec celle utilisée en dev (`docker compose up -d postgres api`, ports `5432`/`5000`) — ni la base de données, ni les conteneurs. D'où des noms de service, ports, `container_name` et **nom de projet Compose** (`name: eventco-e2e` en tête de fichier) tous distincts : sans ce `name` explicite, Compose dérive le nom de projet du nom du dossier et les deux fichiers (situés côte à côte) partageraient le même projet par défaut, au risque d'interactions entre les deux stacks. La base `eventco_e2e` étant neuve à chaque run, `globalSetup` la migre lui-même (`dotnet ef database update --project src/EventCo.Infrastructure --startup-project src/EventCo.Api --connection ...`, même commande que celle documentée dans CLAUDE.md pour la base de dev) plutôt que de faire migrer l'API elle-même à son démarrage : pas de branche « migre-toi » conditionnelle dans `Program.cs` pour un besoin qui n'appartient qu'aux tests — `Program.cs` reste identique quel que soit l'environnement qui le démarre. Le volume Postgres n'est pas nommé : `down -v` (en fin de run, y compris si les tests échouent) le supprime, donc chaque run repart d'une base vierge — vérifié en conditions réelles (stack de dev déjà démarrée en parallèle, restée intacte après le run e2e).
> **Décision (2026-09-04)** : à la demande du développeur, un scénario E2E vérifiant un parcours de connexion (magic link) a besoin de récupérer l'email envoyé. `mailpit-e2e` ([Mailpit](https://mailpit.axllent.org/), image `axllent/mailpit`) ajouté à la stack comme faux serveur SMTP, plutôt que de parser les logs Docker de l'API (`LoggingEmailSender`) : `api-e2e` lui envoie réellement les emails (`Email__Smtp__Host=mailpit-e2e`, `Email__Smtp__Port=1025` — bascule vers `SmtpEmailSender`, jusqu'ici non exercé par aucune suite de tests, cf. `DependencyInjection.AddInfrastructure`), et les steps interrogent son API HTTP (`GET /api/v1/search?query=to:<email>` puis `GET /api/v1/message/{id}`) pour en extraire le lien. Plus robuste que les logs : la recherche par destinataire isole correctement chaque scénario même exécutés en parallèle (`fullyParallel`) contre le même conteneur, alors que le message loggé par `LoggingEmailSender` s'étale sur plusieurs lignes de logs entrelaçables entre scénarios concurrents. Image minimale (binaire Go seul) mais avec son propre `HEALTHCHECK` intégré (`mailpit readyz`), repris tel quel dans `docker-compose.e2e.yml` (`depends_on: condition: service_healthy`, comme `postgres-e2e`) ; `global-setup.ts` sonde en plus son API HTTP avant de lancer les tests, même logique que pour `api-e2e`.

Points d'attention (rencontrés en mettant en place ces trois couches, à ne pas re-découvrir) :
- **`@amiceli/vitest-cucumber` : chaque étape Gherkin est un test Vitest à part entière** (pas juste chaque scénario). Un `afterEach(() => server.resetHandlers())` global (dans `src/test/setup.ts`) s'exécuterait donc *entre deux étapes* d'un même scénario et effacerait un `server.use(...)` avant l'étape qui en a besoin. Le reset des handlers MSW se fait par scénario via `AfterEachScenario` dans le fichier `.steps.tsx` lui-même, pas dans le setup global.
- **`loadFeature(path)` ne résout relativement au fichier appelant que la forme `./MonFichier.feature`** (un seul segment, regex interne de la lib) ; tout chemin avec un sous-dossier ou un `../` (nécessaire depuis que `.feature` et `.steps.tsx` ne sont plus colocalisés, cf. `tests/behavior/`) est utilisé tel quel et donc résolu relativement au **cwd** (`client/`, celui du process `vitest`) — d'où les chemins `tests/behavior/features/...` (et non `../../features/...`) dans les `.steps.tsx` de `tests/behavior/steps/`.
- **Les mots de liaison français (`que`, `qu'`) sont retirés du texte de l'étape par le parser** (`Etant donné que je suis sur la page de connexion` → l'étape à enregistrer est `'je suis sur la page de connexion'`, pas `'que je suis sur la page de connexion'`), aussi bien avec `vitest-cucumber` qu'avec `playwright-bdd`.
- **`playwright-bdd`** : les fixtures Playwright (`page`, `testInfo`, ...) sont toutes destructurées d'un seul objet (`({ page, testInfo }) => ...`), jamais passées en second argument comme avec `test()` natif.
- **Captures de référence (`toHaveScreenshot`)** : les fichiers `.feature.spec.js` sont générés (et régénérés) par `bddgen` dans `.features-gen/` (ignoré par git) — sans le configurer, les captures de référence y naîtraient aussi et seraient perdues à chaque régénération. `snapshotPathTemplate` dans `tests/visual/playwright.config.ts` les place hors de `.features-gen`, dans `tests/visual/__screenshots__/` (versionné).
- **E2E nominal** : `VITE_API_URL` doit pointer vers `api-e2e` (`http://localhost:5001`), ni vers l'API de dev (`5000`) ni vers le profil https local (`.env`, `7166`) — fixé par défaut dans `webServer.env` de `tests/e2e/playwright.config.ts`, surchargeable via variable d'environnement.

**Captures de référence (non-régression visuelle) — CI uniquement.**
> **Décision (2026-09-03)** : à la demande du développeur, `npm run test:visual:update` ne doit plus être exécuté en local pour committer de nouvelles références — le rendu des fonts diffère selon l'OS (le poste de dev est sous Windows) et casserait la comparaison une fois exécutée en CI sous Linux. La régénération se fait exclusivement via le workflow GitHub Actions `update-visual-baselines` (déclenchement manuel, `workflow_dispatch`), qui tourne dans la même image Docker Playwright (`mcr.microsoft.com/playwright:vX.Y.Z-jammy`, tag aligné sur la version de `@playwright/test`) que la CI (`.github/workflows/ci.yml`, job `frontend-visual-tests`). Il produit un artefact téléchargeable (`tests/visual/__screenshots__/`) : le développeur le récupère, compare visuellement les changements, puis committe lui-même s'ils sont valides — pas de commit automatique, la validation reste un geste humain explicite. En cas d'échec du job `frontend-visual-tests` en CI, le rapport Playwright (captures attendue/obtenue/diff) est lui aussi remonté en artefact pour permettre cette comparaison depuis la pipeline.

## 3. Conventions transverses

### 3.1 Git
- Branches : `feature/nom-court`, `fix/nom-court`.
- Commits : format court impératif (`Ajoute l'assignation de tâches`, pas `Added task assignment`), un commit = un changement logique.
- Un lot du découpage (voir cadrage, section 6) = idéalement une Pull Request, même en solo, pour garder un historique de review clair.

### 3.2 API
- REST classique, routes au pluriel (`/api/events`, `/api/events/{id}/tasks`).
- Codes de statut HTTP standards (201 à la création, 404 si non trouvé, 403 si droits insuffisants, 400 si validation échouée).
- Validation des requêtes en entrée via FluentValidation (cohérent avec l'approche Application/Commands).

### 3.3 Documentation dans le code
- Pas de commentaires qui répètent ce que le code dit déjà.
- Un commentaire est justifié quand il explique un **pourquoi** non évident (ex: une règle métier particulière, un contournement technique).
